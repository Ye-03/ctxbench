# ctxbench

**你的 LLM 平均每次请求带多少上下文？大部分团队从来没测过。**

一条命令，读你的调用日志，告诉你上下文长度处在什么水平、有多少在白白烧钱。

单文件，零依赖，纯本地计算，不上传任何数据。

---

## 为什么要在意这个

AI 应用的成本几乎完全由 **input token** 决定。而 input 的长度，取决于你往 prompt 里塞了多少东西——历史对话、文档全文、system prompt、工具定义。

大多数团队在做完产品之后，从来没有回头量过这个数字。而它通常是：

```
你以为：  2,000 ～ 3,000
实际情况：20,000 ～ 50,000
```

差一个数量级，就是差一个数量级的钱。

---

## 快速开始

```bash
python ctxbench.py calls.csv
```

不需要安装任何东西。Python 3.8+ 即可。

支持三种输入：

```bash
python ctxbench.py calls.csv          # CSV
python ctxbench.py calls.jsonl        # JSONL（每行一个对象）
cat calls.jsonl | python ctxbench.py -   # stdin
```

列名会自动识别，`input_tokens` / `prompt_tokens` / `input` 都能认出来。认不出就用参数指定：

```bash
python ctxbench.py calls.csv --input prompt_tokens --model model_name
```

## 它会判断什么

| 现象 | 触发条件 | 含义 |
|---|---|---|
| 上下文压缩 | 平均 > 8K | 检查历史拼接、文档塞入、prompt 缓存 |
| 模型路由 | 单模型 > 70% | 集中度风险，且轻任务可能跑在贵模型上 |
| 读多写少 | input / output > 50 | 压缩输入收益最大 |
| 长尾治理 | P99 > 平均 × 5 | 极少数超长请求吃掉大量额度 |

## 常用参数

```bash
--input COL        指定 input token 列名
--output COL       指定 output token 列名
--model COL        指定模型列名
--price-in 2       输入价格（元/百万 token），默认 2.0
--price-out 8      输出价格（元/百万 token），默认 8.0
--target 8000      目标上下文长度，用于估算可压缩量
--json             输出 JSON，便于接入 CI
--quiet            只输出一行结论
```

接 CI 的例子：

```bash
python ctxbench.py calls.csv --quiet
# avg_input=46636 level=严重 excess=83%

python ctxbench.py calls.csv --json | jq .level
# "严重"
```

## 输入格式

**CSV**

```csv
timestamp,model,input_tokens,output_tokens
2026-01-01T10:00:00Z,gpt-x,32000,450
```

**JSONL**

```jsonl
{"model":"gpt-x","input_tokens":32000,"output_tokens":450}
{"model":"gpt-x","input_tokens":28000,"output_tokens":380}
```

**JSON 数组** 也支持。

只需要 `input_tokens` 一列就能跑，其余可选。

---

## 它不做什么

- **不读 prompt 正文**。只统计 token 计数、模型名、时间戳这些元数据
- **不联网**。没有遥测，没有上报，没有「检查更新」
- **不上传**。所有计算在本地完成
- **不改你的代码**。它只是读一份导出文件

---

## 基准线从哪来

`1K–8K / 8K–20K / >20K` 这三档是经验值，不是行业统计：

```
轻量客服机器人        1,000 – 3,000
RAG 知识库问答        4,000 – 8,000
代码助手（含仓库）    10,000 – 20,000
长文档处理            20,000+
```

如果你做的是长文档场景，「严重」不一定是问题。但如果你的场景是对话式助手，平均超过 2 万，那基本可以确定有大量冗余。

---

## 一个真实的观察

我们在一份三万次调用的生产样本上跑过这个工具，看到：

- 平均上下文约 4 万 token，是常见认知的 5–10 倍
- input 成本占 96% 以上
- 单模型承载约七成流量
- 多模态链路的失败率是文本链路的十倍以上

这些数字说明的问题不在模型，在**上下文工程**——一个几乎没人认真做过的环节。
